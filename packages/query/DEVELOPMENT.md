# Developing the Query Package

Developer guidelines for working on `@orval/query` — the TanStack Query generator that targets five frameworks (React, Vue, Angular, Svelte, Solid) from a single codebase via the `FrameworkAdapter` strategy pattern.

## How to Change Framework Behavior

### Change one framework

Edit its adapter file in `src/frameworks/<name>.ts`. The adapter method you override will only affect that framework.

### Change all frameworks the same way

Edit the default implementation in `withDefaults()` (`src/frameworks/index.ts`), or the shared generator that calls the adapter method (`src/query-generator.ts` / `src/mutation-generator.ts`).

### Change all frameworks but one needs special handling

Edit `withDefaults()` for the common case. Then override the method in the divergent adapter's file in `src/frameworks/`.

## How to Add or Modify Adapter Methods

**New defaultable method:** Add to `FrameworkAdapter` interface in `src/framework-adapter.ts`, add to `DefaultableFields` type, implement the default in `withDefaults()`. Adapters that need different behavior override it in their file.

**New required method:** Add to `FrameworkAdapter` interface (NOT to `DefaultableFields`). Must be implemented in every adapter file.

**Rule of thumb:** If most frameworks share the same implementation, make it defaultable. Only use a required method when each framework genuinely needs a distinct implementation.

## How the `prefix` Pattern Works

`src/query-options.ts` uses a string `prefix` (`'Use'` or `'Create'`) instead of framework booleans. Each adapter returns it from `getQueryOptionsDefinitionPrefix()`. This avoids framework conditionals inside shared code — the adapter decides the prefix, shared code just uses it.

## How to Add a New Framework

1. Create `src/frameworks/<name>.ts` with `create<Name>Adapter()` returning `FrameworkAdapterConfig`
2. Implement the required (non-defaultable) methods; override defaults as needed
3. Register in the `switch` in `createFrameworkAdapter()` (`src/frameworks/index.ts`)
4. Add dependency constants and builder in `src/dependencies.ts`
5. Register the dependency builder in the `dependenciesBuilder` map in `src/index.ts`
6. Add a sample app in `samples/` or at minimum a test config in `tests/configs/`
7. Build, regenerate all samples, test

## Testing Strategy After Changes

### One adapter file changed

```bash
vp run -F @orval/query test                                        # Unit tests
vp run -F @orval/core build:debug && vp run -F @orval/query build:debug   # Rebuild
vp run update-samples                                                      # Regenerate ALL samples
# Inspect that framework's sample output
vp run test:cli                                                            # Verify all generated code compiles
vp run test:samples                                                        # Run sample app tests
```

### Shared generator or `withDefaults()` changed

Same steps, but inspect ALL framework samples — changes propagate to every framework.

### Dependencies changed

Also check that imports in generated files are correct (no missing or extra imports).

**Always use `vp run update-samples`** to regenerate across all frameworks. Never regenerate only one sample when shared code changed.

## Snapshot Coverage

All five frameworks this package targets are snapshot covered, Solid included: `tests/configs/solid-query.config.ts` has a `generate:` script in `tests/package.json`, and `tests/api-generation.spec.ts` asserts its output against `tests/__snapshots__/solid-query/`. (`solid-start` is a separate client, generated by `packages/solid-start`, and is covered the same way.)

So a change to `withDefaults()` or to a shared generator shows up as a snapshot diff for all five. Run `vp run -w test:snapshots:update` and read the diff before committing.

`tests/scripts/typecheck-generated.mjs` compiles every generated client, Solid included, so output that looks valid but does not compile fails there rather than reaching a release. The one file still excluded is `generated/mcp/**/server.ts`, with its reason recorded next to the entry.

Three lists have to agree for a client to be covered at all: the config in `tests/configs/`, its `generate:` script, and its entry in the `dirs` array in `tests/api-generation.spec.ts`. Nothing enforces that today — a config missing from `dirs` is generated and typechecked but snapshot-checked by nobody.

## How Solid Query Requires Caller-Supplied Options

Most adapters make the generated options literal type-check with the `as` cast that `generateQueryImplementation` appends to the options factory in `src/query-generator.ts`; `getQueryOptionsDefinition` only supplies the type it casts to. Solid turns that cast off through `shouldCastQueryOptions()`, because it destroys the `initialData` overload discrimination at the `useQuery` call site.

Without the cast, the emitted literal has to satisfy the framework's interface on its own. Two things follow.

First, Solid's `Use*Options` aliases are `Accessor<…>` function types, so `Partial<…>` of one erases every property — the parameter would accept anything and check nothing. `getUserQueryOptionsConstraint()` is the seam that switches to the plain interface: an adapter returns the keys the caller must supply (`require`) and the keys it may not (`exclude`), and the generator renders `options.query` as `Omit<Partial<…>, require | exclude> & Pick<…, require>`, dropping either half when it has no keys. A constraint with only `exclude` reshapes the type without making anything mandatory.

Second, `initialData` is excluded, because an optional-but-present `initialData` matches neither `useQuery` overload. The discrimination is carried instead by the overload signatures that `shouldGenerateOverrideTypes()` emits, where `getInitialDataOptionsType()` picks `initialData` off `ReturnType<…InitialDataOptions<…>>` — the `ReturnType` unwrapping the `Accessor`, exactly as Solid Query's own `queryOptions()` does.

Infinite queries additionally require `initialPageParam` and `getNextPageParam`, which TanStack requires and orval cannot infer. Because the emitted literal ends in `...queryOptions`, requiring a key on the parameter is what makes the literal satisfy the interface with no cast. Keys that `override.query.options` already writes into the literal are subtracted from `require`, so a caller is never asked for something the config already supplied.

Requiring an option makes the whole `options` parameter mandatory, so `widenOptionalPropsToUndefined` rewrites every preceding `name?: T` prop to `name: undefined | T`. Without that, the signature trips TS1016. Only the signatures that end in a mandatory `options` get the widened props — the invalidate helper's trailing `options?` is optional, so widening its props would add a required argument for nothing.

Solid is the only adapter using this today. If you adopt it elsewhere, two things need doing first: the overload prop lists in `overrideTypes` read the `definition` field, and `getHookPropsDefinitions` reads `definition` rather than `implementation` on the Angular and Svelte v6 adapters — both have to be widened on the same condition, or the emitted signatures trip TS1016.

## Common Pitfalls

- **Forgetting `vp run update-samples`** after changing generation logic — CI will catch stale samples as a diff.
- **Testing only one framework** after changing `withDefaults()` or shared generators — regressions in other frameworks won't be caught.
- **Adding `if (isAngular)` in shared generators** — use adapter methods instead. The FrameworkAdapter pattern exists to avoid framework conditionals in shared code.
- **Framework detection helpers in `utils.ts`** (`isAngular()`, `isVue()`, etc.) are for `dependencies.ts` only — never use them in generators or adapter code.
- **Adding a `tests/configs/*.config.ts` without a matching `generate:` script** in `tests/package.json`. `generate-api` is `run-p 'generate:*'`, so a config with no script is generated by nobody and snapshot-checked by nobody. Every config has one today; keep it that way when you add a framework.
